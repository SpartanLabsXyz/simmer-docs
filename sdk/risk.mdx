`simmer_sdk.risk` gives skill authors portfolio-level risk primitives — state that lives *between* trades rather than inside a single order. Use these alongside [position sizing](/sdk/position-sizing): sizing decides *how much*, risk controls decide *whether to trade at all*.

<Note>
  Available in `simmer-sdk >= 0.11.0`.
</Note>

## DrawdownController

A stateful peak-trough tracker with a **sticky auto-halt**. After every realized PnL event, your bot reports the new bankroll. Before placing a new order, your bot asks whether it's still allowed to trade. When the drawdown from the all-time peak reaches your threshold, the controller latches into a halted state and stays halted — **a bounce back does not auto-un-halt**. That decision is deliberately operator-gated.

### Quick start

```python
from simmer_sdk import SimmerClient, DrawdownController

client = SimmerClient()
bankroll = client.get_portfolio()["available_balance"]

dc = DrawdownController(bankroll=bankroll, max_drawdown_pct=0.15)

# After every realized PnL event
state = dc.update(current_bankroll)
if state["halted"]:
    notify_operator(f"Halted at {state['drawdown']:.1%} drawdown")

# Before every new order
if not dc.can_trade():
    return  # skip trading this cycle

# Operator-initiated recovery (after you've investigated what went wrong)
dc.resume()
```

### API

| Method / property | Description |
|-------------------|-------------|
| `DrawdownController(bankroll, max_drawdown_pct=0.15)` | Constructor. `bankroll` seeds the initial peak. `max_drawdown_pct` must be in the open interval `(0, 1)`. |
| `update(new_bankroll) -> {"drawdown": float, "halted": bool}` | Record the current bankroll. Bumps the peak on new highs. Triggers halt when `drawdown >= max_drawdown_pct`. |
| `can_trade() -> bool` | `False` while halted, `True` otherwise. Call before every new order. |
| `resume() -> None` | Explicitly clear the halt flag. Does **not** reset the peak — future drawdowns are still measured against the all-time high. |
| `peak` | Highest bankroll observed (monotonic). |
| `current` | Most recent bankroll passed to `update()`. |
| `drawdown` | Current drawdown fraction from peak, in `[0, 1]`. |
| `halted` | Whether the controller is currently halted. |
| `max_drawdown_pct` | The configured halt threshold. |

### Semantics

- **Halt threshold is inclusive**: `drawdown >= max_drawdown_pct` triggers the halt. A 15% drawdown against a 15% threshold halts.
- **Peak is monotonic**: it only climbs. A recovery to a new high raises the peak; a dip does not lower it.
- **Halt is sticky**: once halted, even hitting a new all-time high will not clear the flag. Only `resume()` does.
- **Resume preserves the peak**: next drawdown is measured against the all-time high, not the post-resume bankroll. If you want a fresh start, construct a new controller.
- **Per-trade vs portfolio-level**: this is a *portfolio-level* circuit breaker. It does not know about individual orders or market conditions. Pair it with per-trade sizing (see [Position Sizing](/sdk/position-sizing)).

### When to call `update()`

Call `update()` after any event that changes your realized bankroll:

- After an order fills, with the post-fill portfolio total
- After a market resolves, with the post-payout portfolio total
- Periodically from a heartbeat loop using the latest `get_portfolio()` reading

Unrealized mark-to-market swings will feed through `update()` too — that's a design choice. A deep drawdown in open positions is a signal worth halting on, even if it hasn't settled yet.

### When to call `resume()`

Only after an operator has investigated the halt. The intent is that a 15% drawdown represents something outside the bot's normal operating envelope — a bad probability model, a stale price feed, an unexpected market regime — and a human should confirm the cause is understood before re-engaging.

A routine bot restart should **not** auto-resume. Persist the halt state alongside your bankroll checkpoint.

## Balance pre-flight — `client.ensure_can_trade()`

A one-call pre-flight that catches underfunded wallets *before* you try to place an order. Every rejected trade round-trips to the backend, logs a failure, and gets retried on the next cron tick — replacing the loop with a single status fetch per run is a pure win for skill reliability and observability.

<Note>
  Available in `simmer-sdk >= 0.11.1`. Collateral-agnostic — reads pUSD on V2 (post-2026-04-28 cutover), USDC.e on V1, so it keeps working across the migration without any code change on your side.
</Note>

### Quick start

```python
from simmer_sdk import SimmerClient

client = SimmerClient()
preflight = client.ensure_can_trade(min_usd=1.0)

if not preflight["ok"]:
    # Skip cleanly — harness + automaton reporting distinguish this from "skill broken"
    print(f"Skip: {preflight['reason']} (balance ${preflight['balance']:.2f} {preflight['collateral']})")
    return

# Cap your per-run size to leave room for fees + slippage
order_size = min(MY_MAX_BET, preflight["max_safe_size"])
```

### Arguments

| Arg | Default | Meaning |
|---|---|---|
| `min_usd` | `1.0` | Minimum viable trade size in active collateral. Below this, `ok=False`. |
| `venue` | client's venue | Only `"polymarket"` runs the check. Other venues short-circuit to `ok=True`. |
| `safety_buffer` | `0.02` | Fraction of balance kept as fee/slippage buffer. `max_safe_size = balance × (1 − safety_buffer)`. |

### Returns

A dict with the following keys:

| Field | Meaning |
|---|---|
| `ok` | `True` if balance ≥ `min_usd` (or non-polymarket venue). |
| `balance` | Active collateral balance in USD-equivalent units. |
| `collateral` | `"pUSD"` (V2), `"USDC.e"` (V1), or `""` (non-polymarket). |
| `exchange_version` | `"v1"` or `"v2"` — matches server-side flag. |
| `reason` | `"ok"`, `"insufficient_balance"`, `"no_wallet"`, `"balance_unavailable"`, or `"skipped_non_polymarket"`. |
| `max_safe_size` | `balance × (1 − safety_buffer)`, or `0.0` when `ok=False`. |

### When to call it

Call `ensure_can_trade()` **once per skill run**, before any market discovery or signal generation. Running it at the top of your loop costs one REST call and eliminates every downstream rejected order when the wallet is under-funded.

- **Underfunded** → emit a skip report (`skip_reason="insufficient_balance"`) and `return`. The automaton reporter will surface this cleanly, distinct from "skill broken."
- **Sized correctly** → clamp your per-run `MAX_BET_USD` (or equivalent) to `max_safe_size` so you leave headroom for fees + price slippage.

### Why not just trust `client.get_portfolio()`?

You can — but `ensure_can_trade()` bundles three things you'd otherwise re-implement in every skill:

1. **Collateral-agnostic balance selection**: reads the correct token for the active `exchange_version` (pUSD on V2, USDC.e on V1).
2. **Failure-mode distinction**: returns a stable `reason` string across RPC outages, missing wallets, and genuine zero-balance cases.
3. **Safety buffer math**: the `max_safe_size` return is already clamped for fees and slippage — no off-by-one between skills.
