`simmer_sdk.execution.await_fill()` is a thin execution-layer wrapper that polls an open limit order and returns one of four terminal statuses, giving you a structured wait-vs-cancel decision without hand-rolling a state machine.

<Note>
  Available in `simmer-sdk >= 0.10.1`. Opt-in — `client.trade()` does not call this by default. Use it when you care about partial-fill discipline; skip it for fire-and-forget market orders.
</Note>

## When to use it

Limit orders on Polymarket fill partially — the taker side may only eat 30% of your resting quote before the price moves away. You have three bad choices without a wait wrapper:

1. **Block forever** on the remainder and hold stale exposure.
2. **Cancel immediately** and miss the fills that would have come in the next few seconds.
3. **Reinvent the wheel** in every skill with ad-hoc `time.sleep()` loops.

`await_fill()` codifies the pattern: wait for a configurable fraction of the target, cancel cleanly past a time threshold, and always return within `max_wait`.

## The four statuses

| Status | Trigger |
|---|---|
| `FILLED` | `filled / target >= accept_pct` (default 0.95) — remainder auto-cancelled if < 100% |
| `PARTIAL` | `filled / target >= partial_exit_pct` **AND** `elapsed >= max_wait × partial_exit_time_frac` (defaults 0.50 past 70% of the timeout) |
| `TIMEOUT_PARTIAL` | `max_wait` elapsed with any fill |
| `TIMEOUT_NO_FILL` | `max_wait` elapsed with zero fill |

The three thresholds are caller-configurable. Defaults match the commodity "accept 95%, bail at 50% past 70%" pattern walked through in public Polymarket bot guides — override if your strategy has a different risk profile.

## Quick start

```python
from py_clob_client.client import ClobClient
from simmer_sdk.execution import await_fill, clob_poll_fn, clob_cancel_fn

clob: ClobClient = ...  # your authenticated py_clob_client

# Submit a limit order the usual way, get back an order_id …
order_id = "0xabc…"
target_size = 100.0  # contracts

result = await_fill(
    order_id=order_id,
    target_size=target_size,
    max_wait=30.0,  # seconds
    poll=clob_poll_fn(clob),
    cancel=clob_cancel_fn(clob),
)

if result.status == "FILLED":
    # 95%+ filled — remainder already cancelled if any
    ...
elif result.status == "PARTIAL":
    # got >= 50% past 70% of timeout, remainder cancelled
    ...
elif result.status == "TIMEOUT_PARTIAL":
    # ran out of time with some fill, remainder cancelled
    ...
else:  # TIMEOUT_NO_FILL
    # nothing filled, order cancelled
    ...
```

## Tuning the thresholds

```python
await_fill(
    order_id=order_id,
    target_size=100.0,
    max_wait=60.0,
    poll=clob_poll_fn(clob),
    cancel=clob_cancel_fn(clob),
    accept_pct=0.90,             # accept 90% as a full fill
    partial_exit_pct=0.40,       # bail at 40% past the time window
    partial_exit_time_frac=0.60, # arm early-exit at 60% of max_wait
    poll_interval=1.0,           # poll every second (default: 2.0)
)
```

Constraints (enforced at call time):

- All three percentages are in `(0, 1]`
- `partial_exit_pct <= accept_pct` — otherwise the PARTIAL window can never trigger before FILLED
- `target_size > 0`, `max_wait > 0`, `poll_interval > 0`

## The result object

`await_fill()` returns a `FillResult` dataclass:

```python
@dataclass
class FillResult:
    status: FillStatus        # FILLED | PARTIAL | TIMEOUT_PARTIAL | TIMEOUT_NO_FILL
    order_id: str
    target_size: float
    filled_size: float
    fill_ratio: float         # filled_size / target_size
    elapsed: float            # seconds spent polling
    polls: int                # number of poll attempts
    cancel_attempted: bool    # did we call cancel()
    cancel_result: dict | None  # raw CLOB cancel response
    cancel_error: str | None    # if cancel() raised
    last_poll_error: str | None # last poll exception, if any
```

`result.to_dict()` returns a JSON-safe dict suitable for structured logging — `status` becomes a plain string.

## Cancel-failure semantics

If the wrapper decides to cancel the remainder but the CLOB cancel call raises, the wrapper **still returns** the underlying `FillStatus` — cancel errors do not clobber the fill signal. Check `result.cancel_error` to detect a cancel that may not have gone through, and fall back to `client.cancel_order(order_id)` manually if needed.

Likewise, transient poll errors are caught and do not abort the wait. The most recent exception is surfaced in `result.last_poll_error`.

## Custom polling

If you aren't using `py_clob_client` directly, implement `poll` and `cancel` yourself. The `poll` callable receives `order_id` and may return:

- A float / int / numeric string — treated as `size_matched`
- A dict with any of `size_matched`, `sizeMatched`, `filled`, `matched`

```python
def poll_via_sdk(order_id: str) -> dict:
    return client.get_order_status(order_id)  # returns {"size_matched": "…"}

def cancel_via_sdk(order_id: str) -> dict:
    return client.cancel_order(order_id)

result = await_fill(
    order_id=order_id,
    target_size=100.0,
    max_wait=30.0,
    poll=poll_via_sdk,
    cancel=cancel_via_sdk,
)
```

## Relationship to SIM-917

`await_fill()` is an **execution-time** primitive — it runs while an order is open, synchronous with the submitting caller. It does not replace the [SIM-917 partial-fill backfill/accounting](/sdk/overview) path, which reconciles historical partial fills asynchronously. Use both:

- `await_fill()` at order submit: structure the wait-or-cancel decision
- SIM-917 backfill: catch accounting drift after the fact

## Best practices

- **Default opt-in, not opt-out.** Wrap your limit orders with `await_fill()` when you care about discipline; skip it for fire-and-forget flows. This is intentional — some strategies want to let resting orders work indefinitely.
- **`max_wait` is a hard ceiling.** The function is guaranteed to return inside `max_wait + poll_interval` even if every poll is throwing — safe to call from latency-sensitive paths.
- **Don't set `poll_interval` below 1s on production.** The CLOB rate-limits `GET /order/{id}` per API key.
- **Log the full result.** `result.to_dict()` is JSON-safe — pair it with your trade log so post-trade analysis can reconstruct the wait decision.
